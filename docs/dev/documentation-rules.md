# 文档写入规则

## 先选分类

新增内容前先阅读 [文档分类地图](document-map.md)。优先更新已有规范页，不为同一事实创建第二个来源。

## 内容边界

- 架构当前事实写入 `architecture.md`。
- 文件、符号和模块定位写入 `source-map.md` 或 `key-references.md`。
- 构建命令、工具链和产物写入 `build.md`。
- 修改约束和长期规则写入 `conventions.md` 或本页。
- 当前能力、回归闭环和游戏兼容性写入 `compatibility.md`。
- 外部仓库、格式资料和协议入口写入 `krkrz-compat.md`。
- 插件状态和缺口写入 `plugin-compatibility.md`。
- 外部实现逐项差异写入 `aetherkiri-audit.md`。
- 探针名称、开关、位置和成本写入 `probes.md`；使用探针判断问题写入 `rendering-diagnosis.md`。
- 未完成事项写入 `todo.md`；已确认的长期方向写入 `optimization-roadmap.md`。
- 性能测量方法和验收规则写入 `perf-optimization.md`。
- 单个问题的复现、证据和修复结论写入 `incident-reports.md`，不要写入架构或待办页。
- 稳定 API、ABI、脚本方法和参数契约写入 `api-contracts.md`。
- 可重复测试资源和 fixture 说明写入 `test-fixtures.md`。
- 版本变更和兼容性影响写入 `release-notes.md`。

## 事实与推测

- 区分“代码已存在”“已编译”“已验证”和“推测可用”。
- 外部仓库代码存在不能证明本项目具备同等能力。
- 未经目标平台验证的修复必须标记为待验证。
- 不把个人设备、临时路径、完整日志、截图过程、提交编号或逐次试错写入长期文档。
- 不记录完整用户文本、个人路径、密钥或隐私信息。

## 修改规则

- 中英文页保持同一结构和事实；先改中文，再同步英文，或同一提交完成双语更新。
- 标题使用稳定主题，不使用日期、设备名、个人姓名或临时问题描述。
- 代码引用使用仓库相对路径；外部资料使用统一参考入口。
- 表格只放稳定、可比较的字段；长解释放在表格下方。
- 每个待办必须有范围、验收条件和状态；完成后移除或转为当前事实。
- 每次文档改动运行 `git diff --check`，并确认索引链接和中英文文件成对存在。

## 禁止事项

- 不复制架构、构建、兼容边界到多个页面。
- 不把临时排查日志当成测试报告或长期事实。
- 不为尚未决定的功能写成“已支持”。
- 不创建只有标题、没有用途和后续入口的空文档；占位页必须明确目标和写入条件。
